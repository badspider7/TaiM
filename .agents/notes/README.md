# 项目决策记录

这里保存重要决策的原因、真实考虑过的方案及其代价。当前使用说明、接口和架构说明保存在项目既有文档目录，不在这里重复维护。

## 何时记录

只记录代码、测试和现有文档不能充分解释的长期决策，例如架构选型、数据兼容、模块职责、安全约束和有争议的方案取舍。临时计划、操作日志、机械修改和小型 UI 调整不必单独记录。

## 目录与状态

- `proposed/`：尚未完成的提案。
- `implemented/`：已有实现依据的决定。
- `rejected/`：已明确否决、且否决理由仍有参考价值的方案。

文件名采用 `YYYY-MM-DD-topic.md`，日期是首次提出时间，主题采用小写英文、数字及连字符，例如 `2026-10-15-task-storage.md`。按需创建目录；记录增多后可增加领域子目录。正文以一级标题开头，只有一行 `Status: proposed`、`Status: implemented` 或 `Status: rejected`，与所在目录一致。搜索相关主题时，同时查看提案、已实施和否决记录。

## 内容要求

记录问题、决定或提案、实际考虑过的替代方案及其取舍。已实施记录描述当前事实，并说明影响与限制；提案说明验收条件和风险；否决记录保留原提案及否决原因。没有依据的信息标为待确认，不虚构讨论或验证结果。

必要二级章节如下，按项目语言选择中文或英文名称：

- 所有记录：问题 / Problem、考虑过的替代方案 / Alternatives considered。
- 提案：提案 / Proposal、验收条件 / Acceptance criteria、风险与代价 / Risks。
- 已实施：决定 / Decision、影响与代价 / Consequences、涉及文件、验证与限制、提交追踪。
- 否决：提案 / Proposal、否决原因 / Rejection reason。

每个必要章节写明实际内容；尚未掌握的信息明确注明。已实施记录不保留提案、计划或验收条件章节，以实际影响、验证证据或已知限制替代。

## 实现追踪

- **涉及文件**按职责列出与决定有关的新增、修改、删除文件，说明每组负责什么。已有文件使用仓库相对链接，删除文件保留原路径并注明删除。跨多个决定的测试或共享组件可在相关记录中分别引用。
- **验证与限制**记录已执行的命令、覆盖的关键行为和仍未验证的范围。避免把自动化夹具的验证写成真实发布或生产环境验证。
- **提交追踪**列出实际实现提交的完整 Git hash，可有多个。实现还在工作区时写「未提交」并单独列基准 `HEAD`。如果记录与实现同批提交，在后续文档提交中回填实际实现 hash。
- 一次需求涉及多个可以独立演进的决定时，按决定建记录。相关文件清单用于追溯当前实现，同一决定的后续小修在原记录更新。

## 维护要求

### 状态转换

有实现证据后，将提案移入 `implemented/`，更新状态，将提案改为现在时的决定，并将验收条件和风险整理为实际影响、验证证据或已知限制。方案被明确否决后移入 `rejected/`，更新状态并新增否决原因，保留原提案。部分实现仍为提案；未获回复不代表否决。移动后修复入链。

### 事实与决定

路径、符号名、配置键、默认值或实现机制变化时，在同一次变更中更新相关已实施记录，不追加操作流水。改变决定及其理由时新建记录，不能将原记录改写成相反的决定。

### 新旧记录审查

每篇新记录都应检索相关旧记录，判断仍有效、部分被替代或完全被替代。同一决定优先更新原记录；部分替代要保留仍有效的约束，互相链接并明确替代范围。完全替代也不能丢失独有理由、替代方案、影响和限制；合并前保留这些内容并修复入链。

### 归档与删除

没有明确清理授权时只报告删除或归档候选。不要仅凭年龄、字数或数量清理。仍指导当前工作、解释兼容约束或防止重要误判的记录保持活动状态。

已实施记录仍有历史价值但不再指导当前工作时，可以在授权范围内移入 `archived/`，保留正文及 `Status: implemented`，在状态行下添加 `Archived: YYYY-MM-DD`。修复活动文档的入链，之后不改写归档正文；归档只供历史参考。未完成提案不直接归档，被否决的方案只在仍有参考价值时保留。

## 检查

提交前检查文件名、状态、必要章节、相对链接及实现依据。项目已有校验规则优先；采用上述默认格式时，可使用初始化时提供的轻量校验脚本。脚本检查不代替对理由和实现事实的人工核对。
